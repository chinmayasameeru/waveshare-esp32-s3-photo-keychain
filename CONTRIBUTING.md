# Contributing to Waveshare ESP32-S3 Photo Display

Thank you for contributing.

This project targets the **Waveshare ESP32-S3 2inch No-Touch Display Development Board** and intentionally keeps the stable user workflow simple: select a photo in a desktop browser, flash it over USB, and display it on the LCD.

## Before you contribute

Please confirm that your change is for the **No-Touch** board variant. The Touch-LCD-2 hardware uses different peripherals and pin assignments in places, so code copied from touch-board projects can be incorrect for this repository.

For hardware-related changes, document the exact board model, GPIO changes, and any assumptions about the LCD or Flash layout.

## Development workflow

1. Fork the repository and create a focused branch from `main`.
2. Make the smallest change that solves the problem.
3. Keep the browser flasher and firmware behavior consistent with the README.
4. Build the firmware with the documented Arduino CLI configuration.
5. Test the browser flasher in desktop Chrome or Edge with a real ESP32-S3 board when the change affects flashing.
6. Update documentation when behavior, hardware requirements, or build steps change.
7. Open a pull request with a clear description of the problem, the change, and how it was tested.

## Code guidelines

### Firmware

- Preserve the existing Waveshare No-Touch GPIO mapping unless the change explicitly targets hardware.
- Keep display initialization compatible with LovyanGFX and the ST7789T3.
- Avoid unnecessary dynamic allocation on the main render path.
- Validate Flash-resident photo data before decoding it.
- Keep error handling visible and useful on the LCD where practical.
- Avoid introducing Wi-Fi, BLE, cloud, or other background services into the stable firmware unless the project direction is intentionally changed and documented.

### Browser flasher

- Keep image processing local to the browser.
- Preserve Web Serial compatibility with supported desktop browsers.
- Do not silently add network uploads of user photos to third-party services.
- Keep generated firmware artifacts and source flashing addresses synchronized with the firmware.
- Avoid committing generated binary files outside the `docs/` deployment flow.

### Build and CI

GitHub Actions is part of the release path. Changes to source files, the Arduino toolchain, partition scheme, or browser flasher should be tested by the CI workflow before being considered complete.

## Pull requests

A good pull request should include:

- **What changed**
- **Why it changed**
- **Hardware tested**, if applicable
- **Browser tested**, if applicable
- **Build/CI result**
- Any known limitations or follow-up work

For user-visible changes, include a short before/after description.

## Issues and bug reports

Please include enough information to reproduce the problem:

- board variant;
- operating system;
- browser and version, for browser issues;
- Arduino-ESP32 version, for build issues;
- exact steps to reproduce;
- observed behavior;
- expected behavior;
- relevant serial output, screenshots, or logs.

For hardware failures, identify the exact Waveshare board variant and whether the official factory demo works on the same hardware.

## Commit messages

Prefer short, imperative commit messages, for example:

- `Fix JPEG bounds validation`
- `Improve browser flash progress`
- `Document No-Touch LCD pin map`

Keep unrelated changes in separate commits or pull requests when practical.

## Releases and generated files

The `docs/` directory is generated by GitHub Actions for GitHub Pages. Contributors normally should not hand-edit generated firmware binaries there.

Source changes should be made in:

- `PhotoDisplay/`
- `web/`
- `.github/workflows/`
- documentation files such as `README.md`
